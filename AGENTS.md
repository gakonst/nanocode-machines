# nanocode-machines

`nanocode-mpp` (src/bin/nanocode-mpp.rs) is the Nanocode CLI with Codex and Claude paid per request over MPP sessions through [mpp-rs](https://github.com/tempoxyz/mpp-rs) instead of a ChatGPT or Claude subscription login. It only wires the two SDKs together: `nanocode_cli::run_with` runs the unchanged Nanocode TUI and `exec`, including the CLI's own durability defaults, and this crate adds no durability, library or other surface. Keep generic logic in the SDKs: provider-neutral hooks in gakonst/nanocode and payment logic in mpp-rs.

- `ModelClients::openai_endpoint` and `claude_endpoint` build Nanocode's own Codex and Claude clients for the proxies behind `Mpp`, a `nanocode::http::Layer`. Nanocode keeps building the headers, reading response metadata, mapping errors and decoding SSE; the layer only pays, running mpp-rs's 402 flow with `mpp::client::send_with_exchange` (tempoxyz/mpp-rs#588) over the layer's `Next`, so every attempt goes out through Nanocode's client. Request failures keep the error Nanocode's client reported, including whether a request was retryable, timed out or was never sent; payment failures are not retryable. Responses over MPP are HTTPS with full history replay.
- Each service gets its own wallet clone with `with_sqlite_session_store` (tempoxyz/mpp-rs#589): mpp-rs's MPPx-compatible channel store at `$TEMPO_HOME/wallet/channels.db` (default `~/.tempo/wallet/channels.db`), namespaced by service origin, so each service reuses its channel across processes. Processes can use a channel at the same time: before signing, a voucher starts from the highest cumulative amount and deposit any process recorded in the store (tempoxyz/mpp-rs#596). Before that change, a TUI's next request after an `exec` run on the same channel failed with `voucher cumulativeAmount must be strictly greater than highest accepted voucher`. A process's spend panel computes each request's cost from the change in the receipt's `spent`, so it also counts what other processes spent on the shared channel since its last request. `NANOCODE_MPP_DEPOSIT` sets the session deposit and top-up in base units (default 2 MACH, dozens of Codex requests); the proxies send no `suggestedDeposit`.
- Prepaid vouchers skip the 402 round trip. The proxies' OpenAI and Anthropic session challenges are reusable (mppx `reusableChallenges`, wevm/mppx#1063, tempoxyz/mpp-proxy#407): they stay valid for later requests to the same route until they expire, and each request is charged its own price. With `with_session_prepaid_requests(PREPAID_REQUESTS)` (tempoxyz/mpp-rs#583), after one paid request the provider keeps that many requests' worth of balance, at the latest price, above the receipt's `spent` and sends the voucher with the next request. A `402` resends the request unpaid and falls back to the normal flow. With a top-up amount set, the provider tops the channel up in the background once its deposit no longer covers that prepaid balance plus the next request (tempoxyz/mpp-rs#585 through #587); vouchers are signed while the top-up runs.
- The CLI spawns the warm-up on its runtime: `TempoAccountsProvider::preconnect` sends each proxy an unpaid probe that opens the connection and warms the proxy (its isolate and tokenizer), then restores the selected session channel from the store and chain without paying (tempoxyz/mpp-rs#584, #589). It then sends a second probe naming that channel in `Payment-Session`. The server answers with its session snapshot, from which `prime_prepaid` sizes the first prepaid voucher (tempoxyz/mpp-rs#597). The first request therefore carries its voucher, and when earlier vouchers already cover the server's `spent` (usually, since the proxies return unused estimates), it signs one unit above its last voucher instead of adding the request's price. Each `Mpp` layer runs its service's preconnect once, through a `OnceCell`, and its first request waits for it, so `exec`, which sends its prompt immediately, is primed too. Measured 2026-10-20: `exec -m haiku` runs raised the Anthropic channel's vouchers by 1 base unit each instead of 74,755 and took 1.5–3.7 s; Luna runs took 2.4–2.5 s.
- Metered session responses are mppx SSE streams. The layer attaches a `nanocode::http::EventHook` to each response that hands every named event to `TempoSessionProvider::stream_event` (tempoxyz/mpp-rs#589): it answers `payment-need-voucher` with a voucher and resolves pending opens from `payment-need-voucher` and `payment-receipt`. Nanocode's decoders drop consumed events, and Claude treats mppx's generic `event: message` name as unnamed, as the SSE specification does.
- Spend is part of the TUI. Every paid request, models included (the layer passes the shared `ClientEvents` to `send_with_exchange`), lands in `Payments`' ledger from mpp-rs's `payment.response` events, keyed by host. `ModelClients::panel("/spend", …)` shows it as a block above the composer, sorted by spend: `spend · 0.151395 MACH` over one row per service with model or tool, amount, request count, last charge and, for sessions, the deposit left (`TempoSessionProvider::spend().remaining`, from the session providers `Payments::sessions` registers). `/spend` hides and shows it, `exec` prints it after the turn, and the footer keeps only `spent 0.151395 MACH`.
- Without a Tempo Accounts store the CLI exits and asks the user to run `tempo wallet login`.
- Mercator is a built-in MCP server. `ModelClients::mcp_server("mercator", …)` registers https://mercator.sh/mcp, the legacy route that takes MPP payments through MCP metadata, and Nanocode adds its tools to both backends (deferred and in Code Mode, found through `tool_search`). `McpPayments` implements Nanocode's `McpPaymentProvider` with mpp-rs's `mcp::client::McpPayment` on the wallet, without a session store because Mercator takes one-time charges only: a `-32042` payment-required answer to `create_job` is paid and the call retried with the credential, and the response's receipt reaches `McpPending::receipt` so the payment lands in the spend panel and as a notice. Mercator still requires a quote: the agent runs `quote_plan` and passes `quote_token` and `approved_total` to `create_job` within the user's budget. Measured 2026-10-19: a San Francisco weather job paid 0.001 USDC.e to mercator.sh and returned the result; the wallet funded it with MACH through the swapper, and since tempoxyz/mpp-rs#595 the wallet reports that (`PaymentProvider::funding_currency`, read before the MCP payment commits), so the panel labels it MACH even though Mercator's receipt carries no `fundingCurrency`.
- The wallet prefers MACH with `TempoAccountsProvider::with_preferred_currency`: a TIP-1034 session denominated in MACH wins, then a machine-token-enabled charge paid with MACH through the canonical swapper, then the first offer in Accept-Payment order (sessions before charges). This mirrors Mercator's MACH-first charge ordering.
- `OPENAI` and `ANTHROPIC` are the `serviceUrl` entries for `openai` and `anthropic` in https://mpp.dev/api/services. Since tempoxyz/mpp-proxy#394 their model routes offer only `tempo/session`, in USDC.e and MACH, with `unitType: request`, `feePayer` and `feeToken` USDC.e. `tempo/charge` in USDC.e and pathUSD with `machineTokenEnabled` is offered only to requests carrying a charge credential or an `Accept-Payment` header that ranks `tempo/charge` above `tempo/session`.
- The proxy charges a request-priced session stream once and passes the upstream bytes through with their event names and a `Payment-Receipt` header. Its `Server-Timing` header reports `mpp;dur`, the proxy's own time, and `upstream;dur`, the provider's time to response headers.
- `AcceptPaymentPolicy::Always` applies because the layer only receives the model endpoints configured on Nanocode; the management client's redirects are disabled. A retried model request pays for its own unit again.
- A model turn that fails with a retryable error after its retries stays pending in Nanocode's durability, so later prompts on that agent return `blocked by unfinished operation` until the host resumes it; the Nanocode TUI resumes it automatically. A connection that was never established is reported as unsent, so Claude retries it instead of treating its outcome as unknown.
- Tool traffic pays too. `Payments::pay_tools` binds mpp-rs's `ForwardProxy` (tempoxyz/mpp-rs#590) and hands its `environment()` to `ModelClients::tool_environment`, so every shell and Bash process Nanocode starts for a tool gets `HTTPS_PROXY` with a per-process credential and a CA bundle (`SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, `NODE_EXTRA_CA_CERTS`, `NODE_USE_ENV_PROXY`) while nanocode-mpp's own environment and in-process clients stay untouched. The proxy loads https://mpp.dev/api/services on its own thread and intercepts those origins plus `*.mpp.tempo.xyz`, Tempo's own proxies, since the directory omits some of them (fal's queue host `fal-queue.mpp.tempo.xyz`, where fal's video models run): a plain `curl` to a listed service gets its 402 paid with a per-origin copy of the tool wallet (`with_sqlite_session_store` keeps the wallet's session settings since tempoxyz/mpp-rs#594) and retried, and every other host is a plain tunnel. Tool sessions open with `NANOCODE_MPP_TOOL_DEPOSIT` and top up by the same amount (default 0.1 MACH, a hundred requests at the proxies' $0.001 RPC price), so a session-only service a tool touches does not lock the models' 2 MACH. Paid `text/event-stream` responses pass through unchanged while the wallet answers mppx `payment-need-voucher` events through `PaymentProvider::stream_event` (tempoxyz/mpp-rs#592). The model endpoints are in `NO_PROXY` because the HTTP layer already pays them from the same channel store. If the directory fails to load, only Tempo's proxies are intercepted and the status line says `mpp.dev directory unavailable`. Measured 2026-10-19: curl, Node `fetch` and Python `urllib` paid storage.mpp.tempo.xyz (0.0001 MACH each) while example.com, `git ls-remote` and `gh` tunneled; api.aisa.one rejects every credential with `Invalid Challenge` (also with `tempo request`), and Cloudflare answers Python's default user agent with 403 on storage.mpp.tempo.xyz.
- `Payments` turns mpp-rs's payment events into `ModelClients::notices` lines, which the TUI adds to the transcript and `exec` prints to stderr, for tool payments only; model requests appear in the panel, not the transcript. The proxy's `payment.response` events carry the URL, receipt and what the request cost (tempoxyz/mpp-rs#591, #592): a charge's amount, or a session's change in `spent` from its receipt, labelled with the token the wallet spent (`PaymentResponseContext::funding_currency`, tempoxyz/mpp-rs#595), else the receipt's `fundingCurrency`, else the challenge's currency. Every wallet, the models' included, gets the same `ClientEvents` through `with_session_events`, so `channel.deposit` events report each accepted channel open and each top-up, background ones included (`opened a 0.100000 MACH session with rpc.mpp.tempo.xyz`, `topped up the openai.mpp.tempo.xyz session by 2.000000 MACH`). Measured 2026-10-19 through `ForwardProxy` with a 0.002 MACH deposit: six rpc.mpp.tempo.xyz calls reported the open, three background top-ups and a 0.001 MACH cost each, and an openrouter.mpp.tempo.xyz stream passed through on a new channel. No proxy has sent `payment-need-voucher` to a tool yet, so that path is unexercised outside the models' layer.
- Codex's standalone web search (`/v1/alpha/search`, 0.01 USD) and image generation go through the same HTTP layer as model requests (gakonst/nanocode e8c9c572d), so they are paid and land in the model's row of the spend panel. A Responses request that waits 300 s for headers, a body chunk or a payment event now fails retryably instead of hanging the turn. Since tempoxyz/mpp-proxy#413 the proxy prices GPT-6 models at OpenAI's published token rates instead of its 0.01 USD per 2,000 tokens fallback: a 40,000-token Luna request is quoted 0.0045 instead of about 0.2, and a 15-request Codex turn with web search, a Mercator job and a tool payment cost 0.057 MACH on 2026-10-20.
- Streamed model requests pay per token as output is delivered (tempoxyz/mpp-proxy#421). The voucher accepted with the request pays its input estimate and at most 1,024 tokens of output. The estimate prices every input token as uncached, at the cache-write rate when the request marks cache breakpoints. While the stream runs, the proxy deducts each further 1,024 tokens of output from the channel's voucher balance before forwarding them. When the balance runs short, it sends a `payment-need-voucher` event, which the layer's `EventHook` answers through `TempoSessionProvider::stream_event`, and holds the stream until the voucher arrives. The final usage event settles the request at its reported usage, with cache hits at each model's listed rate: the proxy charges any shortfall, such as reasoning that was never streamed, before forwarding the event, and credits back any overpayment. The proxy settles the highest voucher on chain, so a credit stays in the channel for later requests rather than returning to the wallet. The panel counts a request at what its `Payment-Receipt` header shows, its up-front charge; the in-stream charges and the settlement show up in the next request's receipt. Measured 2026-10-20 with `exec "Reply with exactly: ok"`: Sonnet 5 0.034868 MACH (1.495 before), Opus 5.5 0.069736 (about 3 before), Haiku 5.5 0.001743 (0.074755 before). A Haiku stream of 2,691 output tokens on a fresh 0.05 MACH channel paid 0.001 up front, answered two `payment-need-voucher` events of 0.000589 each and settled at 0.001552. Nanocode sends Claude 5.x models `max_tokens` 128,000, which no longer affects the up-front charge.
- Install with `cargo install --path . --bin nanocode-mpp --locked`; `/reload` re-executes it from PATH. The CLI rejects `--gateway` because the Codex client is supplied.

## MACH sessions

Since T12 (mainnet 2026-10-13), TIP-1095 checks a TIP-1034 channel's TIP-403 policy on the logical payer-to-payee path and refunds the payer without it. A MACH session is therefore an ordinary TIP-1034 channel in MACH to a payee on MACH's recipient policy 582. tempoxyz/mach#93 added the MPP proxy payee `0xca4e835F803cB0b7C428222B3A3B98518d4779Fe` to that policy.

- A MACH channel cannot pay its own gas. Sponsored opens pay gas in the challenge's `feeToken` (tempoxyz/mpp-rs#582), and unsponsored opens need `with_session_fee_token`.
- mppx `compose()` dispatched every session credential to the first session handler, so the proxy rejected MACH opens with a currency mismatch. tempoxyz/mpp-proxy#395 routes MACH session credentials itself; wevm/mppx#1060 fixes `compose()`.

## Development

- Do not add code comments, doc comments, README files, tests or test-only dependencies. The user maintains README files.
- Nanocode, its CLI (`nanocode-cli`) and mpp-rs are pinned by git revision; `nanocode` and `nanocode-cli` share one gakonst/nanocode revision, which must include `ModelClients::openai_endpoint`, `notices`, `panel`, `tool_environment` and `mcp_server`, and mpp-rs points at a tempoxyz/mpp-rs main revision that includes #581 through #597 with the `forward-proxy` feature. If cargo cannot fetch a revision, set `CARGO_NET_GIT_FETCH_WITH_CLI=true`.
- Check with `cargo fmt --check`, `cargo check --bins` and `cargo clippy --all-targets`.
- The ignored `output/validation` consumer was written against the removed `MppLayer` library and no longer builds. Real payments spend the wallet's funds; run them only with the wallet owner's approval.
- 2026-10-19 mainnet results with wallet `0x9759…e122` and its P-256 access key:
  - MACH-funded charges completed Codex (Luna) and Claude (Haiku 5.5) turns, spending 0.049925 and 0.074382 MACH.
  - USDC.e TIP-1034 sessions completed Codex and Claude turns, including top-ups.
  - After mpp-rs reused RPC connections, challenge-to-credential time for MACH charges fell from 1.11–1.18 s to 0.25–0.31 s.
  - An unpaid 402 from the proxy took 0.5–3 s, and `/.well-known/mpp` took 0.5–0.8 s.
  - MACH sessions opened sponsored 0.30 MACH channels for Codex and Claude and completed turns, spending 0.051685 and 0.148863 MACH. The wallet's MACH balance fell by exactly the two deposits.
  - Proxy time (`mpp;dur`) for a warm paid session request fell from 1263 ms to 103–129 ms (tempoxyz/mpp-proxy#397 through #405). Vouchers are accepted against on-chain state verified within 60 s (mppx `voucherStateMaxAge`, wevm/mppx#1062) while the chain read runs in the background, so what remains is one Durable Object read (~50 ms) and one compare-and-swap (~60 ms). Isolated requests still spike to 1.5–3 s. A warm voucher takes 4–16 ms on the client; the first payment in a process restores the channel from SQLite and chain state. The unpaid 402 round trip costs 24–155 ms per request.
  - With prepaid vouchers, requests after the first carry their voucher on the first send: 3–15 ms to sign, then one round trip, with `mpp;dur` of 83–105 ms on warm Codex turns. A larger request with a voucher on an earlier, cheaper challenge was charged its own price (15140 against a quoted 1000). Codex turns cost about 0.015–0.02 MACH each because the 45 KB Codex instructions and tools are priced as input, so 0.30 MACH top-ups ran every few turns and each added an on-chain transaction to its turn.
  - With background top-ups, eighteen consecutive Codex turns sent every voucher with the first request after turn 1 (11–34 ms to sign) and took 1.9–5.4 s each, model time included; three 0.30 MACH top-ups ran without delaying a voucher. One turn failed once with a body decode error mid-stream and did not recur.
  - After tempoxyz/mpp-proxy#411 (wevm/mppx#1065), a warm prepaid request makes one Durable Object round trip, the compare-and-swap that accepts the voucher and charges the request: `mpp;dur` 53–70 ms, with the first body byte arriving with the headers.
  - `nanocode-mpp exec --ephemeral -m luna -t low "Reply with exactly: ok"` took 3.5 s wall from process start, and 4.5 s with `-m haiku`.
  - Through the layer on Nanocode's own clients, Codex turns took 1.9–4.1 s and Claude turns 0.9–1.9 s after the first, with each voucher signed in 10–36 ms and sent with its request; `nanocode-mpp exec` answered in 4.5 s (Luna) and 2.2 s (Haiku 5.5) from process start.
  - A cold proxy isolate spends about 0.4 s (measured locally in workerd) building the o200k tokenizer on its first priced request; tempoxyz/mpp-proxy#408 caches token counts of long strings, so a resent history prices in under 1 ms. `preconnect` took 0.8–2 s and hides these first-request costs.
